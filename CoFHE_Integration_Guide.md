# 🤖 👨‍💻 AI & Developer Master Guide: BlindPay Escrow (CoFHE Sepolia)

**Context for AI Assistants (Cursor, ChatGPT, Claude):**
You are assisting a developer in building a full-stack DApp (Next.js Frontend + Backend API) that interacts with a **Fhenix CoFHE Smart Contract** deployed on standard **Sepolia Testnet**.

This contract performs Fully Homomorphic Encryption (FHE) computations asynchronously using an off-chain Coprocessor.

**CRITICAL RULE:** Do NOT use standard `fhenixjs` byte encryption (`encrypt_uint128()`). You MUST use the specific CoFHE SDK provided by the hackathon (e.g., `@cofhe/sdk` or `@fhenixprotocol/cofhe-sdk`), which returns Tuples/Structs containing `ctHash` and `signature` generated by an off-chain Key Management Service (KMS).

---

## 🏗️ 1. Smart Contract Architecture (`BlindPayEscrow.sol`)

The contract acts as a blind escrow.
- The merchant's required price is encrypted.
- The user's paid amount is encrypted.
- The contract evaluates `FHE.gte(paid, required)` to prove payment sufficiency without revealing amounts.

### The EVM ABI Struct Requirement
Whenever you see `InEuint128` or `InEaddress` in the ABI, you must pass this exact Tuple from JavaScript:
```javascript
{
  ctHash: BigInt or String,
  securityZone: Number (uint8),
  utype: Number (uint8),
  signature: String (Hex Bytes)
}
```

## 🎨 2. Frontend: UI/UX & Data Processing

The Frontend's job is to collect the Merchant's desired price, encrypt it via the CoFHE KMS, and submit the creation transaction.

### UI Flow
1. **Input:** Merchant enters the price (e.g., 50 USDC).
2. **Action:** Clicks "Create Payment Link".
3. **Processing:** The app connects to the CoFHE KMS, encrypts the `50`, and signs the transaction via MetaMask/Rabby.
4. **Output:** The app displays the generated `requestId` (a `bytes32` hash emitted in the `RequestCreated` event) as a QR Code or shareable link.

### Frontend Code Execution
```javascript
import { ethers } from "ethers";
import { CofheClient } from "@cofhe/sdk"; // Use actual package name

async function createRequest(merchantSigner, priceInUSDC) {
    const contract = new ethers.Contract(CONTRACT_ADDRESS, ABI, merchantSigner);

    // Initialize CoFHE Client (Frontend automatically uses localStorage for keys)
    const cofheClient = new CofheClient({ network: "sepolia" });

    // ENCRYPT via KMS -> Returns the { ctHash, signature, ... } Struct
    const inAmountStruct = await cofheClient.encrypt(priceInUSDC, "uint128");

    const merchantAddress = await merchantSigner.getAddress();
    const inMerchantStruct = await cofheClient.encrypt(merchantAddress, "address");

    const expiryTime = Math.floor(Date.now() / 1000) + 86400; // 24h

    // Submit the Structs to Sepolia
    const tx = await contract.createRequest(inAmountStruct, inMerchantStruct, expiryTime);
    const receipt = await tx.wait();

    // Extract the requestId from the event logs
    const event = receipt.logs.find(log => log.eventName === 'RequestCreated');
    return event.args.requestId;
}
```

## ⚙️ 3. Backend: Processing & The `fheKeyStorage` Fix

The Backend acts as the Oracle. It watches the standard Sepolia blockchain for USDC transfers. When a user pays, the backend encrypts the *actual* amount received and submits it to the contract.

### 🚨 CRITICAL SERVER ERROR FIX
If your Next.js API route throws: `TypeError: Cannot read properties of undefined (reading 'fheKeyStorage')`
**Why:** The SDK tries to save FHE keys to the browser's `window.localStorage`. In Node.js/Next.js servers, `window` is undefined.
**Fix:** You must pass a mock in-memory storage dictionary when initializing the client.

### Backend Code Execution (Next.js API Route)
```javascript
import { ethers } from "ethers";
import { CofheClient } from "@cofhe/sdk";

export async function POST(req) {
    const { requestId, actualAmountPaid } = await req.json();

    const provider = new ethers.JsonRpcProvider(process.env.SEPOLIA_RPC_URL);
    const backendWallet = new ethers.Wallet(process.env.BACKEND_PRIVATE_KEY, provider);
    const contract = new ethers.Contract(CONTRACT_ADDRESS, ABI, backendWallet);

    // FIX FOR SERVER-SIDE CRASH: Mock localStorage
    const memoryStorage = {};
    const cofheClient = new CofheClient({
        network: "sepolia",
        fheKeyStorage: {
            getItem: (key) => memoryStorage[key] || null,
            setItem: (key, value) => { memoryStorage[key] = value; },
            removeItem: (key) => { delete memoryStorage[key]; }
        }
    });

    // Encrypt the Paid Amount via KMS
    const inPaidAmountStruct = await cofheClient.encrypt(actualAmountPaid, "uint128");

    // Submit to Sepolia
    const tx = await contract.submitPayment(requestId, inPaidAmountStruct);
    await tx.wait();

    return Response.json({ success: true, message: "Sent to Coprocessor" });
}
```

## 🔍 4. How to Detect Payments per Merchant

Because the `merchantEnc` address is completely encrypted on-chain, **you cannot filter blockchain events by the Merchant's wallet address.** The blockchain is blind.

To map payments to merchants, you must use an off-chain Database (Supabase, PostgreSQL, Firebase).

### The Tracking Architecture
1. **Creation Phase:** When the Merchant creates a request on the Frontend, capture the emitted `requestId`.
2. **Database Save:** Save to your database:
   `{ requestId: "0x123...", merchantAddress: "0xABC...", status: "pending" }`
3. **Payment Phase:** The Payer visits the link `yourdapp.com/pay/0x123...`. They send USDC. Your backend detects the USDC transfer associated with that specific payment session.
4. **Resolution Phase:** Your backend calls `submitPayment(0x123...)` on the contract.
5. **Webhook/Polling:** Your backend listens to the `PaymentResolved` event on the contract.
   ```javascript
   contract.on("PaymentResolved", async (requestId, isPaid) => {
       if (isPaid) {
           // Lookup merchant in DB using requestId
           // UPDATE database SET status = 'paid' WHERE requestId = requestId
           // Notify Merchant via WebSocket/Email
       }
   });
   ```

By mapping the public `requestId` to the plaintext `merchantAddress` in your private off-chain database, you maintain perfect on-chain privacy while retaining full dashboard functionality for your users.
